# Ad Client Manager — выпуск, приёмка и ручное развёртывание

**Дата:** 21.10.2026. **Состояние:** только рабочая ветка `feature/integrated-client-workflow`, основной PR #2 — Draft, 87% ориентировочной готовности. На Hostinger новая версия **не опубликована**. Настоящие данные вводить **нельзя** до прохождения всех ворот ниже.

## Принцип: ничего не выпускать автоматически

- Изменение `main` запускает только проверки CI; оно **НЕ** переносит файлы в `deploy`.
- PR и обычный `workflow_dispatch` с `confirm_release=NO` также только проверяют код.
- Публикация доступна только при ручном запуске workflow **из ветки `main`** с параметром `confirm_release=YES`, после `verify=SUCCESS`.
- Публикуются только `index.php`, `.htaccess` и `app/` в существующую ветку `deploy`, через которую настроен Hostinger auto-deploy. БД и приватные PDF/конфиг GitHub не переносит.
- Все опасные действия — merge PR, ручной `YES`, переключение/миграция БД и ввод клиентов — только после отдельного согласования пользователем. Пробная установка в изолированной среде — не разрешение обновить живую.
- CI блокирует ослабление этого условия через `tests/release_policy.py`. После перевода репозитория в Private повторно проверять доступность GitHub Actions, ограничения тарифов и триггеры деплоя.

## Ворота A. Автоматические тесты и исходники

- Убедиться, что `feature/integrated-client-workflow` на актуальном HEAD, PR #2 OPEN DRAFT и не объединён.
- Запустить проверку именно на актуальном SHA: PHP lint, MySQL 8, вход/роли, финансы/валюты/возвраты, клиенты/архив, задачи/напоминания, CSV, приватный PDF, HTTP E2E, SQL+PDF восстановление. Все verify jobs = `SUCCESS`; publish job = `SKIPPED`.
- Проверить, что никакие реальные клиенты, финансовые записи, конфиги, дампы и PDF не попадали в публичный GitHub или Actions артефакты. CI проверяет лишь часть файлов — **историю GitHub нужно дополнительно проверить вручную**.

## Ворота B. Изолированная проверка инфраструктуры Hostinger

**Подробная пошаговая инструкция безопасного стенда:** [`docs/HOSTINGER-STAGING.md`](HOSTINGER-STAGING.md). **Внимание:** test-root не может быть подпапкой существующего `public_html` — из-за вычисления `dirname(__DIR__,2)` есть риск переиспользовать живые конфиг/PDF. Никаких действий на Hostinger до отдельного согласования владельцем.

1. Не трогать работающую БД, конфиг и PDF. Создать **новую** тестовую MySQL-базу и закрытую папку PDF вне `public_html`; использовать только синтетические данные. Не использовать общий SSH для перезаписи существующих сайтов.
2. Развернуть копию рабочего кода в отдельно выделенной тестовой папке/домене, не изменяя действующий Hostinger auto-deploy. Создать отдельный конфиг с тестовыми реквизитами **вне** её веб-корня. Не помещать конфиг в GitHub или чат.
3. Для **новой** тестовой БД запустить `adc_schema($db)`; для имитации обновления старой структуры проверить обе миграции (`payment_events.submission_key` и `billing_periods.creation_key`) сначала только на восстановленной копии. Запуск `adc_schema` **может изменять структуру**; он не является read-only проверкой.
4. Из CLI отдельной тестовой инсталляции запустить `php scripts/release_preflight.php --verify-pdfs` (этот инструмент не входит в автоматическое копирование файлов на `deploy`; для проверки на Hostinger его нужно безопасно разместить отдельно, только вне публичного доступа). Скрипт делает только `SELECT/SHOW` и проверяет конфигурацию, индексы и хэши активных PDF. Результат PASS не заменяет ручной приёмки. Не запускать против живой БД без разрешения пользователя.
5. Создать комплект резервной копии SQL+PDF, затем **восстановить** его в ещё одну отдельную БД/папку. Сравнить хэши, суммы, пользователей и доступы согласно `docs/RECOVERY.md`. Записать факт успешной ручной проверки. Пока **НЕ ПРОВЕРЕНО**.
6. Убедиться, что конфигурация и PDF закрыты от веб-доступа, нет пути по URL и прав на запись у посторонних; проверить PHP 8.3 и MySQL 8 на тестовом хосте.

## Ворота C. Ручная пользовательская приёмка

Использовать **вымышленные** данные. С директором и сотрудником пройти интерфейс в Chrome/Firefox/Brave, на компьютере и телефоне.

| Сценарий | Ожидаемый результат |
| --- | --- |
| Создать реального вымышленного клиента и отдельного демо, назначить источник | Одинаковые формы и функции; демо отмечен и исключён из реальной аналитики |
| В одном периоде сделать работы «Реклама» 1000 BYN и «Разработка» 250 BYN | Начислено точно 1250 BYN, ориентировочная цена не считается вторым начислением |
| Получить 400 BYN и 300 BYN, сделать возврат 100 BYN | Поступило нетто 600 BYN, долг 650 BYN, все события отражены отдельно |
| Загрузить общий PDF счёт+акт+спецификация, отметить передачу | Документ показывается один раз с несколькими метками |
| Изменить стоимость работы | Старый финансовый PDF устарел; сотрудник не может его скачать/передать |
| Заменить PDF директором и снова передать | Новый PDF доступен, старый остаётся в истории; аудит корректен |
| Отредактировать клиента или сумму из двух вкладок | Устаревшая вкладка не может затереть новую запись |
| Повторить оплату и автосоздание периода через повтор POST | Нет второй оплаты, второго месяца и повторного аудита |
| Закрыть сотрудничество, открыть новое, проверить архив | Деньги и PDF прошлых периодов сохранены, нет пересечений |
| Проверить аналитику и оба CSV, затем удалить демо | Реальные суммы соответствуют ручному расчёту; демо не влияет на итоги |

Отклонения, usability-замечания и проблемы клавиатуры/узких экранов фиксировать как конкретные дефекты. Не объявлять этот этап завершённым только по CI.

## Ворота D. Приватность и согласованный выпуск

**Предварительная read-only ревизия Git-истории:** [`docs/PUBLIC-HISTORY-AUDIT.md`](PUBLIC-HISTORY-AUDIT.md). На просмотренных patch и текстовых файлах не найдено совпадений с проверяемыми шаблонами секретов; это **не** финальная очистка публичного следа, не проверка всех CI-логов/вложений и не PASS Gate D.

1. После готовности к выпуску **обязательно перевести `manufact-test/ad-client-manager` из PUBLIC в PRIVATE** в настройках GitHub. Проверить историю репозитория на реальные данные/секреты, доступ команды, ветки и артефакты. При обнаружении секретов — отозвать/заменить, не пытаться решить проблему только сменой видимости.
2. На PRIVATE заново проверить CI, лимиты GitHub Actions и Hostinger auto-deploy. Подтвердить, что `main` push оставляет `deploy` неизменной.
3. Утвердить откат и восстановление; сохранить контрольные SHA и резервную копию. Отдельно согласовать будущую миграцию существующей БД. Не выкатывать код, требующий новых колонок, пока изолированная миграция не прошла.
4. Только после одобрения пользователя выполнить интеграцию PR #2 в `main`. Проверить verify=SUCCESS и **deploy=SKIPPED**. Не предполагать, что это уже публикация.
5. После всех ворот и повторного явного одобрения запустить GitHub Actions → **Verify and deploy Ad Client Manager** → **Run workflow** → ветка `main` → `confirm_release: YES`. Проверить verify=SUCCESS и deploy=SUCCESS, затем фактическую версию на отдельном адресе Hostinger.
6. Выполнить финальную ручную проверку работы сайта после публикации; только затем разрешить ввод реальных клиентов, PDF и финансов. Прежнюю Excel-историю импортировать только после согласования структуры колонок, не копируя её в публичную GitHub-историю.

## Откат

Если после выпуска возникла ошибка, **не менять сразу БД вручную**. Прекратить новые записи и оценить сохранность данных. Восстановить предыдущую проверенную версию кода через согласованную процедуру для `deploy`; БД/документы возвращать только по проверенному согласованному комплекту SQL+PDF и с пониманием риска потери операций после точки копии. Подробности в `docs/RECOVERY.md`.
