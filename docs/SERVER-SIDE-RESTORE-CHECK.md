## Зачем

На выделенном Hostinger скачать огромную SQL-базу может быть непрактично. Проверять восстановление можно **на стороне сервера**, если оператор заранее независимо создал отдельную временную MySQL-базу и отдельную приватную копию PDF. SQL/PDF не отправляются в GitHub, ChatGPT или на личный компьютер. Это не повод менять действующую БД до получения разрешения.

## Что уже готово в коде

- `scripts/compare_restore.php --compare` — **CLI ONLY, READ ONLY**, доступен в тестовом ZIP и закрыт от HTTP через `scripts/.htaccess`. Источник берётся из существующего приватного `adclients-config.php`, а **цель обязательно отдельная БД с другим именем** и отдельная PDF-папка **за пределами public_html**. Не использует существующий `TEST_DB_*` вне изолированного CI.
- Сверяются 13 ожидаемых таблиц, точное число строк и все содержимое записей (полные SHA-256 отпечатки), сгруппированные суммы начислений, оплат, карточных записей (DECIMAL, без float), fingerprint записей PDF по идентификаторам/хешам и SHA-256 **всех активных ссылочных PDF на обоих хранилищах**. Имена клиентов, деньги, ключи документов и доступы **не выводятся**. Провал любой проверки = BLOCKED.
- Скрипт не запускает `CREATE DATABASE`, `ALTER`, `INSERT`, `UPDATE`, `DELETE`, `mysqldump` или копирование. Он **не делает backup и не делает restore** — это независимое сравнение готовой копии. Исходная и целевая базы должны быть стабильны во время сверки.
- Начиная с SHA `ab87f2385805f5fd96cd349a5229db26646207ed`, дополнительно **каждая строка и каждое поле всех 13 таблиц** сравниваются по SHA-256 в порядке PRIMARY KEY: проверка видит искажение имени клиента, комментария, задачи и прочих нефинансовых данных. Память ограничена потоковым чтением PDO; оба источника читаются в read-only транзакционных снимках MySQL. Это криптографический контроль **логического содержимого записей**, но не байтовая идентичность сырых файлов MySQL или дампа. Не заменяет ручную проверку входа, работы с карточками, восстановления и согласование релиза.

## Важные ограничения

- Если в живой базе есть новые операции после снятия backup, расхождение ожидаемо — **не замалчивать** и не выполнять повторное восстановление поверх живой базы. Нужна согласованная консистентная точка копии/режим остановки записей.

- GitHub ещё PUBLIC — настоящие SQL, PDF, реквизиты и пароли не должны попадать в репозиторий, Action logs, issue или чат. Перевод в PRIVATE требует отдельного действия владельца и аудита истории.
