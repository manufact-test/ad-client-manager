# Ad Client Manager — приёмка на существующем тестовом Hostinger (Gate B)

**Согласовано владельцем 21.10.2026:** используем уже выделенный для этого приложения сайт `darkred-crow-882796.hostingersite.com`. Другой сайт или поддомен создавать **не нужно**. Владелец сообщил, что существующая база содержит лишь данные первичной настройки директора, но **это предположение до фактической проверки и создания резервной копии**.

**Ничего не менялось в Hostinger из GitHub:** доступен только GitHub-коннектор, а не hPanel/SSH/SFTP. Этот документ готовит короткий безопасный сценарий, который владелец сможет выполнить в Hostinger. `main`, `deploy` и Hostinger auto-deploy остаются нетронутыми. Готовность 87%, Gate B/C/D не пройдены.

## 1. Что использовать и чего не делать

- **Рабочий тестовый сайт:** `https://darkred-crow-882796.hostingersite.com/`; его существующий `public_html` и существующая тестовая БД. Сохранить учётную запись директора, данные и конфигурацию.
- **Для проверки восстановления** создать позднее *одну дополнительную временную* MySQL-базу и отдельную приватную PDF-папку за пределами web root. Не создавать ещё один публичный сайт. Никогда не перезаписывать существующую БД ради restore.
- **Не использовать** базу, файлы, Cron или `public_html` других сайтов на аккаунте Hostinger, и не менять настройки автоматики существующего деплоя.
- Исходники ищут `adclients-config.php` и `adclients-documents` в `dirname(__DIR__,2)` относительно `app/core.php` / `app/documents.php`. В выделенном корне сайта это родитель `public_html`. **Запрещено** размещать тестовый код в `public_html/subfolder`: тогда вычисленные пути изменятся.
- До PRIVATE GitHub — только вымышленные пользователи, имена, суммы и PDF. Настоящий пароль или SQL-дамп не присылать в GitHub, чат или Actions.

## 2. Сохранить текущие данные ДО замены файлов

1. В hPanel выбрать **только** указанный тестовый сайт; сверить выделенный ему document root и родительскую папку с приватными `adclients-config.php` и `adclients-documents`. Не открывать/копировать их содержимое в переписку.
2. Создать резервную копию файлов текущего `public_html` (в отдельной приватной папке или локально), независимо от GitHub `deploy`. Экспортировать **текущую тестовую БД** целиком через phpMyAdmin → Export → SQL. Дамп хранить приватно **вне `public_html`**, не прикреплять в PR.
3. Если `adclients-documents` содержит PDF — сохранить её отдельную приватную копию вместе с SQL; иначе зафиксировать «папка пуста». Это необходимо для согласованного SQL+PDF rollback.
4. Подтвердить, что в БД действительно нет важных данных. Не удалять директора и не выполнять DROP/TRUNCATE. Записать в приватном протоколе дату копии и SHA пакета.

## 3. Получить тестовую сборку (без merge и публикации)

- В PR #2 на актуальном SHA открыть успешный GitHub Actions run → **Artifacts** → `adclient-staging-<SHA>`. Внутри скачанного artifact находится `ad-client-manager-staging.zip`. Этот ZIP формируется **только после SUCCESS verify** и содержит только `index.php`, `.htaccess`, `app/*.php`, `app/.htaccess` и три защищённых CLI-файла `scripts/`.
- `actions/upload-artifact` не публикует сайт и не меняет `deploy`/Hostinger. Не использовать архив случайного старого SHA.
- Сохранить приватный конфиг и PDF **на местах**. После резервной копии распаковать содержимое staging ZIP **в корневую папку выделенного тестового сайта `public_html`**, с сохранением `.htaccess` и перезаписью только перечисленных файлов приложения. Не распаковывать `adclients-config.php`, SQL или настоящие данные (их в сборке нет).
- На короткий интервал между заменой файлов и миграцией вход может не работать; не вводить данные, пока проверка схемы не завершена.

## 4. Проверить схему и сохранить директора

Из доверенной SSH/Hostinger CLI перейти в `public_html` **этого** сайта. Сначала выполнить только read-only диагностику:

```bash
php scripts/staging_migrate.php --plan
```

Инструмент ничего не изменяет в режиме `--plan`: убеждается, что доступны 11 таблиц, приватный конфиг и активный директор; показывает только наличие двух нужных новых `nullable UNIQUE` полей без значений/паролей.

**Только после резервного SQL+PDF комплекта и подтверждения правильной тестовой БД**:

```bash
ADC_STAGING_MIGRATE=CONFIRM_TEST_SITE php scripts/staging_migrate.php --apply
php scripts/release_preflight.php --verify-pdfs
```

`--apply` запускает существующий идемпотентный `adc_schema` для этой тестовой базы; **MySQL DDL не откатывается транзакцией**, резервная копия обязательна. Сначала обработать любую ошибку, не продолжать приёмку, если миграция/диагностика отказали. `release_preflight.php` работает только на чтение, не делает ALTER/UPDATE. `scripts/.htaccess` запрещает доступ к обоим CLI-скриптам по веб-URL.

Если **SSH в hPanel недоступен**, не заменять эти команды бесконтрольным SQL в phpMyAdmin. Зафиксировать блокер и выбрать отдельный проверенный способ выполнения команд с доступом только к нужной тестовой базе.

## 5. Ручная проверка Gate C после PASS

Сначала войти в приложение существующим директором. Потом пройти с вымышленными данными: создать сотрудника и клиентов реальный/демо, начислить 1000 BYN за рекламу + 250 BYN за разработку, получить 400 + 300, вернуть 100 → нетто 600 BYN и долг 650 BYN. Проверить один PDF с метками счёт+акт+спецификация, замену устаревшего файла, передачу сотрудником, старые вкладки, архив/возобновление, задачи, CSV, аудит и исключение демо. На Chrome/Firefox/Brave и телефоне, с клавиатурой.

Данные *физически* остаются тестовыми; отметка `is_demo=0` у вымышленного клиента нужна лишь для проверки аналитики. **Не** загружать реальные Excel, клиентов, счета или персональные данные в PUBLIC GitHub.

## 6. Восстановление SQL+PDF (отдельная копия, без второго сайта)

- Создать одну временную MySQL-базу только для restore, с отдельным пользователем и минимальными правами. Импортировать **только** сохранённый тестовый SQL-дамп. Скопировать сохранённые вымышленные PDF в другую приватную папку вне web root.
- Сравнить число строк всех 11 таблиц, ключи/индексы, историю директор/сотрудник, начисления/валюты, передачу, аудит, SHA-256 PDF. Пока это не выполнено на Hostinger, статус B7/B8 — **НЕ ПРОВЕРЕНО**.
- Для функциональной проверки восстановленной копии нельзя просто подменить живой `adclients-config.php`. Использовать изолированный CLI с отдельным приватным конфигом/контролируемую offline-проверку; публичный тестовый сайт должен продолжать смотреть только в свою исходную БД.
- Не удалять временную копию до сверки. После успешной приёмки удалить **только** специально созданные временные ресурсы, сохранив согласованную резервную копию.
