# Ad Client Manager — изолированный стенд Hostinger (Gate B)

**Дата подготовки:** 21.10.2026. **Статус:** инструкция, **на Hostinger ещё не выполнялась**. Согласованная готовность продукта: 87%, без изменений до фактической приёмки.

Связанные документы: [RELEASE.md](RELEASE.md), [ACCEPTANCE.md](ACCEPTANCE.md), [RECOVERY.md](RECOVERY.md). Никаких команд ниже не выполнять на существующей БД, действующем сайте, общем домене или `deploy`. Работа на Hostinger только после отдельного согласования владельцем.

## 0. Стоп-условия перед любым действием

- У владельца должна быть подтверждённая **новая тестовая область** (отдельный домен/поддомен и собственный документ-корень), **новая MySQL-база и отдельный MySQL-пользователь**, доступный только к тестовой базе. Не использовать реквизиты текущего приложения.
- Исходный `main`, `deploy`, существующие авторазвёртывания, Cron Jobs, конфиги, SQL-дампы и `adclients-documents` не изменяются.
- **Нельзя устанавливать стенд в `public_html/test` существующего приложения.** `app/core.php` и `app/documents.php` используют `dirname(__DIR__, 2)`; такая папка может начать читать *общий* родительский `adclients-config.php` и *общие* PDF.
- Если у нового поддомена физический web root всё-таки находится **внутри** `public_html` существующего сайта, установка запрещена до исправления структуры. Новые staging и restore-корни должны иметь собственные родительские каталоги и не наследовать текущий конфиг/хранилище.
- Ни реальные клиенты, ни их PDF, ни старые таблицы Excel не нужны. Нельзя прикладывать секреты/снимки конфигов к Issue, PR, чату или CI.

## 1. Физическая изоляция файлов

Пример **структуры**, а не действующих путей Hostinger:

```text
<isolated-staging-root>/
  adclients-config.php            # уникальные staging credentials (приватно)
  adclients-documents/            # приватные staging PDF; изначально пусто
  public_html/                    # document root только тестового адреса
    .htaccess
    index.php
    app/
    scripts/                      # только для временной CLI-проверки; deny web
<isolated-restore-root>/
  adclients-config.php            # уникальные credentials второй восстановленной DB
  adclients-documents/            # восстанавливаемые PDF
  public_html/                    # отдельная копия кода для проверки восстановления
```

Скрипты рассчитывают родительскую папку из `public_html/app`, а не из доменного имени. **Проверка путей обязательна:** реальные `adc_config_path()` и `adc_doc_directory()` должны указывать только в новую staging-папку. Никаких symlink в живые каталоги. Права: приватные каталоги доступны только служебному пользователю PHP; PDF `0600`, папка предпочтительно `0700`. Документы не должны иметь публичного URL.

## 2. Подготовка в hPanel владельцем (без передачи секретов)

1. Создать новый тестовый поддомен/домен с независимым физическим web root, SSL и настройкой PHP **8.3+**. Адрес тестового входа должен быть закрыт от посторонних (например, отдельная HTTP Basic Auth/доступ только с доверенных IP), дополнительно к логину приложения. `noindex` не является защитой доступа.
2. Создать отдельную пустую MySQL 8 базу и отдельного пользователя **только с правами на неё**. Не давать права на существующие БД.
3. В родительской папке нового web root создать уникальный `adclients-config.php` по требуемому формату `adc_config()` (секрет `setup_secret` минимум 24 символа), создать закрытый `adclients-documents/`. Пароли и секрет генерации хранить только на стороне Hostinger. Создать отдельные credentials для restore-области.
4. **До загрузки кода** письменно подтвердить лишь нейтральные факты: «новый поддомен; отдельный web root; две отдельные тестовые БД; два приватных PDF-каталога; PHP 8.3+». Не пересылать пароли, имя аккаунта Hostinger, SQL-дампы или конфиги.
5. Никакого ручного GitHub Actions `confirm_release=YES`. Тестовую версию копировать **только в тестовый web root**, из проверенного SHA feature-ветки. Автодеплой рабочего сайта не изменять.

## 3. Безопасная последовательность испытаний

| № | Проверка | Критерий PASS | Статус |
| --- | --- | --- | --- |
| B1 | Отдельные web root, SQL пользователи, конфиги и PDF | Реальные пути staging/restore физически и логически отделены от существующих; нет symlink | НЕ ПРОВЕРЕНО |
| B2 | Test-only PHP, MySQL, TLS, внешняя HTTP-защита | PHP 8.3+, MySQL 8; чужим без допуска недоступно | НЕ ПРОВЕРЕНО |
| B3 | Первичная установка на пустой тестовой БД | Только вымышленный директор, 11 таблиц, работает вход | НЕ ПРОВЕРЕНО |
| B4 | Миграция схемы на **третьей одноразовой тестовой копии** | Старые nullable ключи мигрируют, старые платежи/периоды сохраняются, повторный `adc_schema` не меняет данные | НЕ ПРОВЕРЕНО |
| B5 | Read-only preflight с `--verify-pdfs` | PASS, обе новые UNIQUE колонки/индекса, активный директор, SHA-256 всех активных PDF | НЕ ПРОВЕРЕНО |
| B6 | Private PDF / config web-access | Прямой HTTP доступ к приватным файлам, `app/` и `scripts/` запрещён | НЕ ПРОВЕРЕНО |
| B7 | SQL + PDF согласованная резервная копия | Никаких пропущенных таблиц/PDF, дамп не расположен в public_html | НЕ ПРОВЕРЕНО |
| B8 | Восстановление в **новую** БД+PDF+код без переключения живого | Совпадают строки, суммы по валютам, пользователи, аудит, хэши; вход/скачивание на восстановленной копии | НЕ ПРОВЕРЕНО |
| B9 | Негативная проверка | Повреждённый staging PDF блокирует скачивание и делает preflight FAIL, после восстановления оригинала — PASS | НЕ ПРОВЕРЕНО |

**Только после предварительной проверки изоляции B1** открыть тестовый адрес и создать первого директора через штатную форму с уникальным staging-секретом. `adc_schema` создаёт/мигрирует таблицы и **не является read-only**: не вызывать на живой БД. Для B4 нужен *отдельный* одноразовый снимок синтетической БД; не делать `DROP INDEX/COLUMN` на staging БД, которую используют люди.

`scripts/release_preflight.php` запускается из доверенной командной строки внутри копии приложения:

```bash
php scripts/release_preflight.php --verify-pdfs
```

В web root скрипт допускается только с `scripts/.htaccess` (запрет HTTP доступа); после проверки временный CLI-инструмент можно удалить из публичного document root стенда. В CI он уже проверен, на Hostinger — **нет**. Утечки полных путей, содержимого config или вывод SQL с данными недопустимы.

Для B7/B8 использовать порядок и инварианты из `RECOVERY.md`, обязательно сохранять одну согласованную точку **SQL+PDF**. Копию восстанавливать в отдельный restore-root (с самостоятельным config и собственной БД), а не путём переназначения config работающего стенда. Откат проверки = отключить только тестовую копию; исходные приложения и данные остаются нетронутыми.

## 4. Подготовка ручной приёмки Gate C

Завести двух **вымышленных** пользователей (директор/сотрудник), одного «реального» только по флагу программы, одного demo. Финансовый контроль из `RELEASE.md`: 1000+250 BYN начислено, 400+300 BYN получено, 100 BYN возвращено = 600 BYN нетто, 650 BYN долг. Проверить общий PDF с метками, старую/новую версии, смену пароля, повторный POST, архив/возврат, обе CSV, демо-исключение. Chrome/Brave/Firefox + смартфон, клавиатура, длинные формы. Только вымышленные суммы/имена/PDF.

## 5. Форма доказательства выполненных проверок

В отдельном локальном/приватном протоколе (без SQL, файлов и секретов) сохранить: дату, SHA feature, версию PHP/MySQL, test/restore **условные имена без паролей**, результаты B1–B9 PASS/FAIL, количество проверенных PDF и контроль того, что реальные ресурсы не изменились, краткие дефекты Gate C, лицо, подтвердившее визуальную проверку. Не превращать FAIL или «не выполнялось» в PASS.

## 6. Следующий безопасный шаг

**Для подготовки стенда достаточно подтверждения владельца, что разрешено создать НОВЫЕ test-only ресурсы в Hostinger.** До такого разрешения B1–B9 остаются НЕ ПРОВЕРЕНО и никаких действий в Hostinger не делать. Если доступ к Hostinger недоступен через коннектор, владелец создаёт только изолированные ресурсы; разработчик готовит код, проверку GitHub/CI и точный сценарий без запроса паролей.

После B/C не пропустить Gate D: завершить аудит **всей** PUBLIC-истории и CI-артефактов, перевести репозиторий в **PRIVATE**, перепроверить Actions quota и auto-deploy, получить отдельное разрешение на merge, миграцию и ручной релиз.
